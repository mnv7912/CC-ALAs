import os
import platform
import socket
from datetime import datetime
import psutil
from flask import Flask, request, redirect, render_template_string

app = Flask(__name__)

DATABASE_URL = os.environ.get("DATABASE_URL", "")
if DATABASE_URL.startswith("postgres://"):
    DATABASE_URL = DATABASE_URL.replace("postgres://", "postgresql://", 1)


def get_db():
    if DATABASE_URL:
        import psycopg2
        return psycopg2.connect(DATABASE_URL), "PostgreSQL (Managed Cloud DB)"
    import sqlite3
    return sqlite3.connect("local_fallback.db"), "SQLite (Local Storage)"


def init_db():
    conn, _ = get_db()
    cur = conn.cursor()
    if DATABASE_URL:
        cur.execute("""
            CREATE TABLE IF NOT EXISTS deployment_logs (
                id SERIAL PRIMARY KEY,
                node_name TEXT NOT NULL,
                note TEXT NOT NULL,
                created_at TEXT NOT NULL
            )
        """)
    else:
        cur.execute("""
            CREATE TABLE IF NOT EXISTS deployment_logs (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                node_name TEXT NOT NULL,
                note TEXT NOT NULL,
                created_at TEXT NOT NULL
            )
        """)
    conn.commit()
    cur.close()
    conn.close()


init_db()


@app.route("/")
def index():
    conn, db_type = get_db()
    cur = conn.cursor()
    cur.execute("SELECT id, node_name, note, created_at FROM deployment_logs ORDER BY id DESC LIMIT 10")
    rows = cur.fetchall()
    cur.close()
    conn.close()

    vm = psutil.virtual_memory()
    return render_template_string(
        HTML,
        hostname=socket.gethostname(),
        db_type=db_type,
        os_info=platform.system(),
        py_ver=platform.python_version(),
        cpu_count=psutil.cpu_count(logical=True),
        mem_used=round(vm.used / (1024 * 1024), 1),
        mem_total=round(vm.total / (1024 * 1024), 1),
        rows=rows,
    )


@app.route("/add", methods=["POST"])
def add():
    node_name = request.form.get("node_name", "").strip()
    note = request.form.get("note", "").strip()
    if node_name and note:
        conn, _ = get_db()
        cur = conn.cursor()
        ts = datetime.utcnow().strftime("%Y-%m-%d %H:%M:%S UTC")
        placeholder = "%s" if DATABASE_URL else "?"
        cur.execute(
            f"INSERT INTO deployment_logs (node_name, note, created_at) VALUES ({placeholder}, {placeholder}, {placeholder})",
            (node_name, note, ts),
        )
        conn.commit()
        cur.close()
        conn.close()
    return redirect("/")


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=int(os.environ.get("PORT", 5000)))

Comparative Analysis of Cloud Security Architectures: IAM, Cryptography, and Data Protection Across Major CSPs

Review Activity analyzing the Shared Responsibility Model, Identity & Access Management, Envelope Encryption, Confidential Computing, Real-World Breaches, and Zero Trust Best Practices.

1. Abstract

Enterprise migration to public cloud infrastructure transforms security engineering from static network-perimeter defense to identity-centric, software-defined governance. Operating under the Shared Responsibility Model, Cloud Service Providers (CSPs) secure physical facilities, hypervisors, and network fabrics (security of the cloud), whereas tenants remain accountable for Identity and Access Management (IAM), cryptographic key governance, and data protection (security in the cloud). This review paper evaluates Amazon Web Services (AWS) as the primary reference architecture—benchmarked against Microsoft Azure and Google Cloud Platform (GCP)—across IAM models, encryption protocols, data protection controls, real-world breach root causes, and Zero Trust best practices.

2. Core Security Architecture Analysis (Reference Platform: AWS)

2.1 Identity and Access Management (IAM)

  • Hybrid RBAC & ABAC Authorization: Combines Role-Based Access Control (RBAC) with Attribute-Based Access Control (ABAC) using session tags and JSON policy conditions (aws:PrincipalTag, aws:SourceIp), scaling authorization without policy sprawl.
  • Short-Lived Federated Credentials: Replaces static API access keys with enterprise Identity Provider federation via SAML 2.0 and OpenID Connect (OIDC). The AWS Security Token Service (STS) issues temporary, auto-rotating credentials scoped to bounded session durations.
  • Organizational Guardrails & Policy Logic: Enforces multi-account permission ceilings via Service Control Policies (SCPs) and Permission Boundaries. Policy evaluation defaults to implicit deny, while any explicit deny overrides all allow rules.

2.2 Cryptographic Controls & Envelope Encryption

  • Data at Rest & Envelope Encryption: Standardizes on AES-256-GCM via AWS Key Management Service (KMS) backed by FIPS 140-3 Level 3 validated Hardware Security Modules (HSMs). Storage services encrypt datasets locally with a unique plaintext Data Key, which is wrapped by a root Customer-Managed Key (CMK) and stored alongside the ciphertext.
  • Data in Transit & Hardware Nitro Encryption: Enforces TLS 1.3 with Perfect Forward Secrecy across public endpoints, paired with automatic hardware-level encryption between AWS Nitro EC2 compute instances inside VPCs.
  • Key Sovereignty Tiers: Supports CSP-managed keys, Customer-Managed Keys (CMKs) with automated rotation, Bring Your Own Key (BYOK) from on-premise HSMs, and Hold Your Own Key (HYOK) via KMS External Key Store.

2.3 Data Protection & Confidential Computing

  • Access Guardrails & WORM Immutability: Account-level S3 Block Public Access overrides permissive bucket ACLs, while S3 Object Lock enforces Write-Once-Read-Many (WORM) retention in Compliance Mode to prevent ransomware deletion.
  • Automated Data Loss Prevention (DLP): Amazon Macie applies machine-learning classifiers across S3 buckets to discover exposed PII, financial records, and leaked credentials.
  • Confidential Computing in Use: AWS Nitro Enclaves create isolated, hardened vCPU and memory partitions without persistent storage or external networking, protecting sensitive data in use from host inspection.

3. Comparative Security Matrix: AWS vs. Microsoft Azure vs. Google Cloud Platform

4. Real-World Cloud Breach Scenarios & Root Cause Analysis

Case 1 • SSRF & IAM Over-Privilege 2019

Capital One Data Breach

Attack Vector: Exploited a misconfigured ModSecurity WAF on an AWS EC2 instance to execute Server-Side Request Forgery (SSRF) against the EC2 Instance Metadata Service (IMDSv1 at 169.254.169.254), harvesting temporary IAM role credentials.

Impact & Root Cause: Over-permissive IAM roles (s3:ListBucket, s3:GetObject) enabled exfiltration of 100M+ customer records. Root cause: lack of least-privilege IAM scoping and unauthenticated IMDSv1.

Case 2 • Cloud Misconfiguration 2023

Toyota Connected Cloud Exposure

Attack Vector: A cloud database and storage environment remained publicly accessible without authentication due to improper access control lists (ACLs) and lack of automated configuration drift alerting.

Impact & Root Cause: Exposure of approximately 2.15 million vehicle location histories and terminal identifiers. Root cause: absence of continuous Cloud Security Posture Management (CSPM) and automated public-access guardrails.

5. Zero Trust Best Practices for Securing Cloud Environments

  1. Enforce IMDSv2 Session Tokens: Mandate session-oriented PUT token headers with restricted hop limits across all compute instances to block SSRF credential theft.
  2. Zero Trust & Least Privilege IAM: Replace long-lived IAM users with federated OIDC roles, mandate FIDO2 MFA, and continuously prune unused permissions with IAM Access Analyzer.
  3. Shift-Left Infrastructure as Code (IaC) Scanning: Integrate static security scanners (Checkov, tfsec) inside CI/CD pipelines to block open security groups or unencrypted storage before deployment.
  4. Immutable Centralized Audit Trails: Stream all API calls (AWS CloudTrail / Azure Activity Logs) into a centralized, WORM-locked Security Log Archive account isolated from production administrators.

1. Case Study Overview

Mission-critical enterprises operating financial, healthcare, and digital platforms rely on hyperscale Cloud Service Providers (CSPs) for continuous uptime and regulatory compliance. This case study evaluates Amazon Web Services (AWS) as a primary enterprise cloud provider, benchmarking its contractual Service Level Agreements (SLAs), monthly downtime budgets, service credit structures, compliance attestations, and operational risks against Microsoft Azure and Google Cloud Platform (GCP).

3. Compliance Frameworks & Regulatory Alignment

  • ISO/IEC 27001 & ISO/IEC 27017 Third-party audited Information Security Management System (ISMS) and cloud-specific security controls attested via AWS Artifact.
  • SOC 1 / SOC 2 Type II Continuous independent validation of operational effectiveness across Security, Availability, Processing Integrity, and Confidentiality trust criteria.
  • DPDP Act 2023 (India) & GDPR (EU) Enforces regional data residency in ap-south-1 (Mumbai) and ap-south-2 (Hyderabad), Data Processing Addendums (DPAs), and cryptographic right-to-erasure controls.
  • PCI-DSS v4.0 & HIPAA Level 1 PCI Service Provider attestation and HIPAA Business Associate Addendum (BAA) for regulated FinTech and Healthcare workloads.

4. Critical SLA Gaps Identified

  1. Asymmetric Financial Liability: Service credits are capped at 100% of the affected service’s monthly infrastructure fee, never compensating for lost business revenue, customer churn, or regulatory penalties.
  2. Strict Multi-AZ Preconditions: AWS’s 99.99% EC2 SLA applies only when workloads span two or more Availability Zones; single-AZ deployments receive zero SLA credit protection during zone-level outages.
  3. Burden of Proof on the Tenant: Credits are non-automatic—customers must gather independent outage logs and file formal claims within two billing cycles.
  4. Exclusions & Composite Availability Decay: Excludes Force Majeure, external DDoS floods, and tenant misconfigurations. Chaining four serial 99.99%–99.9% services reduces composite end-to-end availability to 99.83% (~74.5 min/mo downtime).

6. Strategic Recommendations

  • Negotiate Custom Enterprise Discount Programs (EDPs): High-spend enterprises should negotiate proactive automated SLA credit triggers and explicit RTO/RPO contractual commitments.
  • Deploy Independent Synthetic Uptime Probes: Operate external synthetic monitors (Prometheus Blackbox Exporter / Datadog Synthetics) to record immutable uptime evidence independent of CSP status dashboards.
  • Maintain Tested Multi-Cloud Exit Portability: Conduct annual disaster-recovery exit drills verifying encrypted backup restoration on a secondary CSP within target RTO windows.

Cloud Performance Engineering: Dynamic Auto-Scaling, Load Balancing, Telemetry, and Edge-Fog Integration

Technical evaluation of Layer 4/7 traffic distribution, elastic scaling policies, Golden Signals observability, 10× traffic spike simulation, and Edge-Fog compute offloading.

1. Core Performance Optimization & Auto-Scaling Architecture

High-performance cloud applications decouple edge caching, request routing, stateless compute pools, and data persistence so each layer scales independently under fluctuating workloads. Figure 1 illustrates the end-to-end elastic topology driven by closed-loop telemetry.

Figure 1: Closed-loop cloud performance optimization architecture with Edge CDN offloading, L7 ALB routing, and telemetry-driven horizontal auto-scaling.

2. Load Balancing & Auto-Scaling Mechanisms

  • Layer 4 (NLB) vs. Layer 7 (ALB): L4 Network Load Balancers forward TCP/UDP packets at ultra-low latency without payload inspection, whereas L7 Application Load Balancers terminate TLS and inspect HTTP paths, headers, and cookies for microservice routing.
  • Vertical vs. Horizontal Scaling: Vertical scaling (Scale-Up) adds vCPU/RAM to a single node (suited for monolithic DBs but bounded by hardware ceilings), while Horizontal scaling (Scale-Out) adds stateless nodes across Availability Zones dynamically.
  • Elastic Scaling Policies: Combines Target Tracking (holding CPU at 65%), Step Scaling (tiered additions on sharp breaches), and ML-Based Predictive Scaling (pre-warming instances ahead of recurring traffic cycles).

3. Cloud Monitoring Metrics (The Four Golden Signals)

1. Latency (Tail Focus)

Tracks P95 & P99 response times rather than averages that hide tail degradation.

2. Traffic Volume

Measures Requests Per Second (RPS) and active concurrent ALB connections.

3. Error Rates

Monitors HTTP 5xx server errors, gateway timeouts, and failed health probes.

4. Resource Saturation

Tracks CPU utilization, memory pressure, and SQS queue depth backlog.

5. Modern Trends: Edge & Fog Computing Integration

Edge Computing Tier 10–25 ms RTT

Executes JWT authentication, geo-routing, asset caching, and lightweight inference directly on global CDN Points of Presence (Cloudflare Workers, AWS Lambda@Edge), eliminating cross-continental round trips.

Fog Computing Tier 60–80% BW Saved

Introduces intermediate local compute nodes (industrial IoT gateways, 5G Multi-access Edge Computing / MEC) that filter, aggregate, and pre-process high-frequency sensor streams locally before transmitting summarized payloads to the central cloud.
